## 2026-09-05 — atomic store writes and fetch timeout

**План.** (A) `saveStore` писал прямо в `data/weatherbot.json` —
при kill -9 или OOM mid-write файл повреждался, все сценарии
пользователей терялись. (B) `fetch` в `weather.js` не имел timeout —
зависший провайдер блокировал `collectWeather` бесконечно.

**Сделано.** (A) `saveStore` пишет в `*.tmp`, затем `rename` —
атомарная операция в POSIX, файл никогда не повредится. (B) Каждый
`fetchJson` создаёт `AbortController` с timeout 10с — если провайдер
не ответил, запрос прерывается и идёт retry.

**Проверено.** `npm run check`: `node --check` + 8 тестов, все зелёные.

## 2026-09-05 — разбиение длинных сообщений

**План.** Telegram ограничивает длину сообщения 4096 символами. При большом
количестве источников и расхождениях блок details мог сделать сообщение
слишком длинным — API вернул бы ошибку.

**Сделано.** `sendMessage` разбивает текст на чанки до 4096 символов,
разрезая по последнему `\n` в пределах лимита. Каждый чанк отправляется
отдельным `sendMessage`. Клавиатура (`reply_markup`) прикрепляется только
к последнему чанку.

**Проверено.** `npm run check`: `node --check` + 8 тестов, все зелёные.

## 2026-09-05 — сериализация saveStore

**План.** `pollOnce` и `sendScheduledForecasts` работают concurrently: обе
могут модифицировать `store` и вызвать `saveStore`, который пишет весь `store`
в JSON. Если две записи в один файл пересекутся, можно потерять изменения или
повредить файл.

**Сделано.** `saveStore` переписан: `JSON.stringify(store)` вызывается
синхронно (фиксирует текущее состояние), а сама запись сериализована через
promise chain (`saveChain`). Каждый вызов ждёт завершения предыдущей записи.
Ошибка предыдущей записи не ломает цепочку (`.catch(() => {})`).

**Проверено.** `npm run check`: `node --check` + 8 тестов, все зелёные.
